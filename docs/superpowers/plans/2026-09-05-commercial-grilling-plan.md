# CheeseWAF 商业化能力 Grilling 规划结果

日期：2026-09-05
状态：规划已确认，已进入分阶段实施（截至 2026-09-11：阶段 0 基线、核心 contract、PG/Redis 适配器、Approval 一致恢复、诊断加密队列、CWEDP/NetLease transport 和 AI 运维批次已有验证；主服务生产生命周期仍未全部接线）
适用范围：CheeseWAF、CheeseSec_Plugin、CheeseSec_Plugin_Docs 及其商店、OTA、CRP、离线交付能力

## 目标

把本次 1–133 项 grilling 结论转成一套可实施的商业 WAF 方案：数据面优先保证可用性，管理面采用最小权限和可审计的确认流程，插件、CRP、商店和集群分发形成可验证的供应链边界，完全离线的集群仍能安装、升级、回滚、恢复和审计。

运维交互采用“首次高风险操作明确确认、同一授权范围内减少重复打扰、任何实质变化重新确认”的原则。安全控制尽量在 broker、控制面、主机网络和密钥提供者层执行，避免只依赖插件自觉或 UI。

## Scope

- In：集群控制面、PG/Redis 使用边界、Token 与 Session、审批和 Break-glass、CRP/商店/OTA、自协商分发、签名根、阈值签名、离线模式、临时联网、诊断上传、加密队列、对象存储、审计、灾备、文档和生产构建门禁。
- Out：本计划不直接实现源码改动；不在第一阶段引入 WASM 插件、DuckLake、插件 Ansible 推送、请求线程内 RPC 或将 DuckDB 放入 WAF 主二进制。

## 实施状态说明（2026-09-11）

本文件继续作为 1–133 项决策基线；源码实施和验证记录以仓库根目录的 `tasks.md`、`docs/acceptance-matrix.md` 和各架构契约为准。当前已经落地并有证据的部分包括：

- 控制面状态、epoch/fencing、native-raft、PostgreSQL/Redis 适配器及严格身份边界；真实 PostgreSQL 17.11 和 Redis 8.0.2 的隔离集成回归已执行。
- CRP manifest/签名/本地暂存 contract；CRP activation service 的 observe→canary→active、精确 last-known-good 回滚和 mTLS transport contract 已有测试，但 CLI 到生产 control-plane/sidecar 的完整挂载仍待完成。
- CWEDP 协议、断点续传、来源隔离、NetLease broker、HTTP/file transport、HTTPS/mTLS/NodeID/leaf pin 和 pre-dial fail-closed；主 `serve`、节点注册、插件安装和生产编排仍待接线。
- temporary→production 迁移的恢复记录、同事务管理状态/旧 Token 元数据、v1 ledger 的 `unverified-v1` 停止路径，以及诊断队列/AI 运维的独立修复批次。
- Approval 持久层现在支持批次原子提交、durable epoch CAS，以及 epoch+record+events 的一致恢复快照；真实 PostgreSQL 已覆盖篡改、回退、checkpoint 缺失和恢复边界。诊断组合运行时已接入 canonical envelope、持久队列、失败可重试 replay reservation 和 metadata-only 审计，但外部对象复制和回执仍未上线。
- temporary-online 已有可复用的 `Broker.ExecuteTemporaryHTTP` 生命周期和 durable revoke 审计；migration/session/fence 组合回归与 CRP 服务端 TLS 监听 contract 已有证据，但主 `serve`、插件控制器和 durable control-plane provider 仍未接线。

这些实现状态不会改变原有安全边界：缺少控制面、sidecar、租约、审批或审计证据时必须停止或保持 last-known-good，不能为了让验收矩阵变绿而绕过依赖。

## 已锁定的总体架构

### 控制面、数据面和部署

- 控制面使用独立的 `cheesewaf-control`；native-raft 管理成员、任期、epoch、fencing 和期望状态，PG 保存管理真相，Redis 只承担短期锁、租约、缓存和安全辅助状态。
- 单节点也沿用同一控制面模型；可使用内建 PG/Redis 兼容能力，但生产 HA 默认采用外部或 Pigsty 适配部署。
- Ansible 只负责基础设施、控制面和分发代理引导；插件 CRP 的安装、升级、回滚由自协商分发协议完成。
- WAF 请求路径保持 34A+：插件全部 sidecar 化，采用异步观察、快照和 hint，不等待插件 I/O，不在请求线程内读取网络、PG、Redis 或 KMS。
- 数据面采用 30D-AU：硬安全边界和管理硬规则保持 fail-closed；模型、审计和响应检查器故障时优先 observe/pass 并标记 `inspection_incomplete`，Availability Guard 只能降低概率性动作。

### 插件、CRP 和信任根

- 官方命名空间采用 63B：离线 Vendor Root、多发布密钥、按风险采用 2-of-3 或 3-of-5 阈值签名。
- 企业命名空间采用受约束 63C：每个企业独立根和发布链，只能签 `enterprise/<org-id>/*`，不能伪装官方包。
- 社区、个人、测试和开发根独立存在，默认不可信；高权限操作继续执行二次确认后的第三次最终确认。
- 65B：密钥采用分阶段双信任重叠轮换。官方和认证企业最长 3 年，社区/个人 1 年，测试 30 天，开发密钥 7 天；到期不回溯打掉已验证 last-known-good，泄露则走紧急吊销。
- 66B：签名发生在密钥有效期内且未被吊销的历史 CRP 仍可运行；新安装、升级、重新启用和正式晋级必须使用有效新密钥。
- 67D：在线包优先使用独立时间证据或透明日志；离线包携带控制面双签快照、单调发布序号和完整来源链。
- 68B：高风险 CRP 要有透明日志证明；低风险和已有运行版本不因日志服务故障中断。
- 69C 为离线默认，69D 为可选高保障：企业本地透明日志负责空网运行，多日志证明在导入前随 CRP 携带。
- 70B/70D：默认使用签名 Air-gap Evidence Bundle；高安全企业可选单向传输站。

### 离线模式和临时联网

- 72A-Ephemeral：离线模式默认无任何外部出站。插件可以通过控制面接口申请一次临时联网，但必须由管理员输入密码确认并写入连接审计。
- 71D：插件默认 `egress=deny`，只允许显式登记的内部资源；业务数据面到已配置 Origin 的流量不受离线模式误伤。
- 74B：插件可以获得一次性受限 Socket Lease，绑定插件版本、目标资源、协议、端口、TLS 指纹、策略代次和短时租约。
- 75C：下载是默认能力；上传必须在签名清单中声明，绑定数据类别、目标、大小和次数，并单独审批。
- 76C/77B：默认上传元数据、健康状态和脱敏诊断包；扫描失败后允许上传固定 Schema 的原始诊断包，但必须经过高风险告警、10 秒等待、密码确认和第三次最终确认。
- 78C/79D：同一包和租约的短窗口可复用确认；平台设置不可突破的传输、重试和持续时间上限，企业只能收紧。
- 80D/81A+B/82D/83B+D/84C/85D/86C/87B/88B：诊断包按风险留存；目标须有声明，原始包优先要求签名回执；Break-glass 由安全或租户最高管理员启用，会话级授权按风险分层过期，插件只能调用 broker 的异步 `upload_diagnostic` API。

### 诊断队列、对象存储和加密

- 89B+D：节点本地加密队列是所有部署的基础，PG/Redis只保存元数据和协调状态；企业可选集群级接管。
- 90B/C、91B：默认本地加密保存；启用企业对象存储时异步复制，外部诊断上传与内部复制并行，不互相阻塞。
- 92B：应用侧信封加密。每个包独立 DEK，对象存储只接触密文和被包装的 DEK；AAD 绑定租户、插件、版本、目标、摘要和策略代次。
- 93B+93D：正常 KEK 轮换异步、按 TTL 延迟重包装；KEK 泄露或滥用时按密钥代次、租户和插件最小范围紧急吊销。

## 运维体验、安全性和复杂度复核

### 运维体验

- 首次高风险操作需要明确确认，但同一会话、同一目标和同一策略范围内减少重复输入。
- 诊断上传统一异步，插件和请求线程不等待远端服务；队列、对象复制和审计均可观察、可重试、可取消。
- 离线模式页面显示外连状态、积压队列、快照代次和风险原因，管理员不需要猜测为什么某项升级被暂停。
- 复杂能力都有安全降级：对象存储、SIEM、透明日志、外部 KMS 或 LLM 故障不会打断已有 WAF 流量。

### 安全性

- 关键完整性门禁仍然强制：签名、阈值、命名空间、摘要、版本、防回滚、吊销和权限范围不能通过“缺证据”绕过。
- 原始诊断上传是高风险例外，固定 Schema、临时租约、短 TTL、字节配额、目标回执和 Break-glass 审计共同限制外泄面。
- 供应链传输源、签名者、发布者和来源独立性分开验证；Peer、镜像和 Ansible 都不能获得发布权限。
- 已运行 last-known-good 和 WAF 数据面优先保持可用，事故处置通过隔离、撤销能力和回滚完成。

### 复杂度

- 第一版不把所有企业能力都做成强制依赖：透明日志、对象存储、外部 KMS、多日志和高保障传输都是可选层。
- 复杂策略统一进入状态机、manifest、策略快照和审计模型，避免每个功能维护一套互相冲突的权限流程。
- 企业可以收紧平台默认上限，但不能放宽签名、租约、留存、网络和高风险确认边界。
- 先交付基础可用路径，再增加高保障模式：单节点/空网可用是底线，企业 HA、WORM、多日志和硬隔离作为增强层。

## 验收门禁

[ ] 干净工作区按 README/中文 README 的 Get Started 完成安装、初始化、启动和最小防护验证。

[ ] 单节点不启动 PG/Redis 时仍能使用临时模式；切换生产模式会完成迁移、确认和临时 Session 失效。

[ ] 集群能够完成节点加入、选举、配置快照、插件 CRP 拉取、断点续传、三种摘要校验和安全回滚。

[ ] 开启离线模式后，控制面、插件和后台任务没有外部出站；业务反向代理仍可正常访问 Origin。

[ ] KEK 正常轮换、KEK 紧急吊销、离线吊销增量导入和恢复凭证流程不影响已运行 WAF。

## 复核结论

这套方案把“可用性优先”落实为管理面和数据面解耦，而不是放宽核心安全边界。日常运维使用会话授权、异步队列和安全重试降低打扰；高风险动作仍有可解释的确认和回滚路径；离线环境具备完整的本地验证、审计、恢复和升级能力；复杂的企业增强能力均不成为单节点或 WAF 数据面的硬依赖。

当前没有阻塞性的产品决策问题。下一阶段的主要工作是把上述状态机、manifest、审计事件和验收脚本落到代码与文档中，并在实现过程中对每项门禁保持中英文同步。
